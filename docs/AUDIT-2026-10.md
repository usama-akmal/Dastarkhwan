# Dastarkhwan — defect, business-risk, and opportunity audit

> **Status update.** The trust-critical findings in §1–§3 have been repaired. See
> "Remediation log" at the end of this document for what changed, how each fix was
> verified, and what deliberately remains open. The original findings are preserved
> below in full so the record of what was wrong stays intact.

**Date:** 2026-10-05
**Revision audited:** `5763b3a` (master, 4 commits, nothing since the MVP landed on 2026-09-16)
**Scope:** 24 source files (~2.6k LOC), 80 seed dishes, Dexie v1 schema, PWA config, GitHub Pages workflow.
**Method:** source reading plus headless execution of the real engine modules against the real 80-dish seed
(harnesses written to `/tmp`, outside the repo). No test runner, no jsdom, no fake-indexeddb, and the dev
server was not run, so no behaviour was exercised against a real IndexedDB or a real browser. Findings
depending on IndexedDB semantics or service-worker behaviour are labelled as such.

---

## Headline

The product's central promise is not delivered in the shipped state.

| Claim (README) | Measured reality |
|---|---|
| "Smart Recommendation Engine" | Winner is decided by seed-table row order plus one random draw; ~98% of outcomes ignore the score |
| "ensures you don't repeat the same dish within 7 days" | Only the *same-dish* rule works; protein and dish-type cooldowns are dead code |
| Family preferences drive suggestions | Onboarding persists **zero** preferences; a rejected dish scores *higher* than an accepted one |
| Dietary rules ("limit beef to X/week") | Every weekly rule is inert; one class of rule blocks 100% of tagged dishes |
| "100% Offline-First" | App shell yes; typography is fetched from Google Fonts at runtime |
| Your data stays on your device | True — and it is the *only* copy. No export, import, or backup exists |

Net: a household that completes onboarding lands in an all-default state where the app is a biased shuffle.
Nothing tells the user this, and there is no telemetry that would tell the maintainer either.

## 1. Correctness bugs in the recommendation engine

### F1.1 — Protein and dish-type cooldowns are dead code [Critical · certain]
`isOnCooldown(dish, cookingHistory, cooldowns, allDishes)` needs `allDishes` to resolve protein/dishType
(`repetitionTracker.js:10`), but `suggestionEngine.js:37` calls it with three arguments. `dishMap` stays `{}`,
and history rows carry only `{ dishId, date, mealType }` (`useSuggestion.js:79-83`), so the lookups at
`repetitionTracker.js:32-33` always yield `undefined`.

Reproduced: `Chicken Karahi` with `Chicken Biryani` (chicken) cooked yesterday →
`{onCooldown:false}` without `allDishes` vs `{onCooldown:true, reason:"Same protein (chicken) made within 3 days"}` with it.

Impact: the "Same protein cooldown" and "Same dish type cooldown" sliders (`SettingsPage.jsx:139-162`) do nothing
for every user. Chicken can be suggested seven days straight.

### F1.2 — `getCategoryCounts` never receives `allDishes`; all weekly rules inert [Critical · certain]
Three call sites pass three arguments (`suggestionEngine.js:27`, `:31`, `:109`) against a four-parameter
signature (`repetitionTracker.js:98`). The return value is therefore always `{proteinType:{}, dishType:{}}`.

Consequences: `max_per_week` compares against `0`, so a "max 1 chicken/week" rule after two chicken meals changes
the available pool by **zero dishes** (78 before and after; 18/20 chicken dishes still offered). And `min_per_week`
(`suggestionEngine.js:113-116`) is permanently true, giving every vegetable dish a constant +5 that never switches off.

### F1.3 — Tag rules count *all* history rows instead of tagged rows [Critical · certain]
`suggestionEngine.js:53-59` computes `tagCount` as the total number of meals logged this week; the tag only decides
which dishes get punished. Reproduced: with **zero spicy meals cooked**, logging 2 non-spicy meals plus a
"max 2 spicy/week" rule blocks **38/38 = 100%** of spicy dishes. Because the engine can only filter, the UI reports
"No suitable dishes found" (`HomePage.jsx:13-21`) and the only recovery is deleting the rule.

### F1.4 — `no_consecutive` on tags reads a map that can never hold tags [High · certain]
`suggestionEngine.js:66-69` indexes `yesterdayCounts.proteinType[rule.value]` where `rule.value` is a *tag*, and
`getCategoryCounts` only ever populates `proteinType`/`dishType` (`repetitionTracker.js:99`). Structurally dead even
once F1.2 is fixed. The protein `no_consecutive` branch is dead for the same reason.

### F1.5 — Settings-created rules use `type`; the engine reads `ruleType` [High · certain]
Stored as `type` (`SettingsPage.jsx:11`, `:178`, `:56`), read as `ruleType` (`suggestionEngine.js:46`, `:62`, `:113`).
Every user-created rule is a silent no-op with a UI that implies enforcement. The rule list also renders from
`rule.type` (`SettingsPage.jsx:221`), so onboarding rules (which use `ruleType`) display as malformed strings.

### F1.6 — `getDietaryRules()` can never match, and is dead code [Medium · certain]
`db.js:76` queries `.where('isActive').equals(1)`, but writers store a boolean (`DietaryStep.jsx:13,16,19,22`) and
Settings-created rules omit the field entirely. IndexedDB keys are typed, so number `1` never equals boolean `true`.
No callers exist, so the bug is latent — but it is a trap for the next one.

### F1.7 — `mealType` is accepted and never used; lunch and dinner draw identical pools [High · certain]
`suggestionEngine.js:20` never references `mealType` (lint confirms). Reproduced: the available-id list for `'lunch'`
is byte-identical to `'dinner'`. Nothing models "lunch is light/quick, dinner is heavier" despite every dish carrying
`light`/`heavy`/`quick` tags. Over 20,000 trials, **P(lunch pick == dinner pick) = 2.6%** — roughly one duplicated
meal every 38 days, with no dedupe and no warning. (A *just-accepted* lunch is excluded from dinner, but only as a
side effect of the coarse 7-day same-dish rule.)

Also an off-by-one: the comparison is `daysSince <= cooldowns.sameDish` (`repetitionTracker.js:13`), so a setting of 7
blocks days 0–7 = **8 days**. Same pattern at `:45` and `:71`.

### F1.8 — `getDaysSinceLastMade` returning `Infinity` is NOT a bug [verified clean]
`Infinity >= 14` is true, so the `+10` is finite and `b.score - a.score` never sees a non-finite value. Residual
(Low): on day one every dish is "never made", so that bonus is a uniform constant carrying no signal.

### F1.9 — Default preference is punitive, and there is no neutral state [High · certain]
`conflictResolver.js:12` coerces an unrated dish to `'eats'`, so "no opinion" and "explicitly eats" are
indistinguishable, and both land in `result.eaters`. `suggestionEngine.js:94-95` then subtracts 10 per eater from a
base of 50. Measured: a 4-member household with nothing rated yields scores of **10–30** across the whole pool
(designed base was 50); an 8-member household drives unrated dishes to **−18**. The "eats" penalty dominates the entire
ranking. README documents three states, but the scorer treats the implicit default as a demerit.

### F1.10 — In the realistic state the engine is not scoring at all [Critical · certain]
All dishes tie at base 20 with no preferences and no history, so `Math.floor(Math.random()*21)-10`
(`suggestionEngine.js:122`) plus a *stable* sort (`:135`) decides everything. Measured over 20,000 trials with the
engine's own draws inspected:
- P(winner drew the maximum offset `+10`) = **100.0%**
- P(winner is the *first* seed row to draw that maximum) = **100.0%**
- Winning-offset distribution: `{+10: 19616, +9: 378, +8: 6}` → ~98% of outcomes ignore the score

Top winners are simply the first seed rows: Biryani 4.68%, Karahi 4.50%, Korma 4.25%, Tikka 4.23%, Butter Chicken
4.06%, Malai Boti 3.79% — against 1.25% for a fair draw. New users get a near-uniform random dish with a strong
first-rows bias.

### F1.11 — Timezone: meals logged 00:00–04:59 local are stored with yesterday's date [High · certain]
Writes use the UTC calendar date (`useSuggestion.js:19`, `:78`, `:90`) while reads build local-time strings and local
midnight (`CalendarPage.jsx:23-24,77,116`; `suggestionEngine.js:4-18`). Reproduced for Pakistan (UTC+5):

```
local 2026-10-05 00:30 PKT -> stored "2026-10-04"   (off by one)
local 2026-10-05 04:30 PKT -> stored "2026-10-04"   (off by one)
local 2026-10-05 05:30 PKT -> stored "2026-10-05"   OK
local 2026-10-05 23:30 PKT -> stored "2026-10-05"   OK
affected local hours: 0,1,2,3,4  (5/24 = 21%)
```

When it bites: the row is dated yesterday, so `loggedMealForToday` returns `null` (no "Planned for Today", no
"✕ Remove"), `cancelPlannedMeal` cannot find it, the meal shows on the wrong calendar cell and can skew weekly stats —
while the dish remains cooldown-excluded. Note the direction flips with the sign of the UTC offset: a UTC−5 user hits
the *evening* window instead.

### F1.12 — `updateSettings` receiving `id: 1` is NOT a bug [verified clean]
Dexie 4.4.6 `Collection.modify` treats an equal primary key as a no-op `put` rather than delete+add, so the whole-object
update at `SettingsPage.jsx:37` is safe. Minor (Low): the `mealsPerDay` radios (`:99-100`, `:112-113`) call both
`handleSettingChange` and a second whole-object `updateSettings`, which could in principle write a pre-blur snapshot.

## 2. Behaviour gaps users will hit

### F2.1 — Onboarding persists nothing: wrong destructure in both steps [Critical · certain]
`useFamilyMembers()` returns `{ members, ... }` (`useDatabase.js:18-30`), but `RatingStep.jsx:7` and `FamilyStep.jsx:6`
destructure `familyMembers`, defaulting to `[]`. The default masks the error silently.

- **RatingStep is a total no-op.** The loop at `:19-22` iterates an empty array, so every ❤️/👍/🚫 tap writes zero rows
  while the progress bar, the 1/30 counter, and the animations all imply success.
- **FamilyStep's list is permanently empty** and its primary CTA is permanently disabled (`:126-127`). The only way
  forward is the wizard footer's "Next →" (`OnboardingWizard.jsx:76-85`).
- Members *are* written to IndexedDB, so a refresh-and-retry adds duplicates (no uniqueness on name), and each
  duplicate silently adds another −10 to every dish while making the "all members love it" bonus unreachable.

### F2.2 — Onboarding's "Won't eat" stores `wont_eat`; the engine only knows `wont_touch` [Critical · certain]
`RatingStep.jsx:136` writes `'wont_eat'`; `conflictResolver.js:13` hard-filters on `'wont_touch'`. A refused dish is
treated as "eats it" and only loses 10 points. Safety-adjacent given allergy/religious framing. Note FamilyPage and the
wizard's Skip button use the correct vocabulary, so the two UIs disagree on the data contract.

### F2.3 — A pending suggestion does not survive a reload; an accepted one does [High · certain]
The pending pick lives only in a `useMemo` over randomised scores; rejections live in component state
(`useSuggestion.js:7`). Measured P(shown dish differs after reload, nothing accepted) = **97.5%** with a clean
profile, **97.2%** with 30 days of history. With `registerType: 'autoUpdate'`, a background SW update that reloads the
page also reshuffles. There is no "this is today's plan" anchor until the user taps ✅.

### F2.4 — "Other options" cards look tappable but have no handler [High · certain]
`HomePage.jsx:133-163` sets `cursor: 'pointer'` with no `onClick`, although `acceptSuggestion(dishId)` already supports
an explicit id (`useSuggestion.js:69-73`). Users must instead spam "🔄 Something Else", which permanently excludes the
top pick and re-rolls everything.

### F2.5 — No way to log a meal the engine did not suggest, and no back-dating [High · certain]
The only write to `cookingHistory` is `acceptSuggestion` (`useSuggestion.js:79`). `addCookingHistoryEntry` /
`deleteCookingHistoryEntry` are exported (`db.js:72-73`) and surfaced by the hook (`useDatabase.js:48-49`) but never
consumed. Reality cannot enter the model: cook something else, eat out, or forget to tap, and cooldowns drift
permanently. There is also no way to log yesterday's dinner.

### F2.6 — Custom recipes cannot be edited or deleted; deleting one would orphan history [High · certain]
`RecipesPage.jsx:5` destructures only `{ dishes, loading, addDish }`; no edit/delete UI exists anywhere. Even if wired,
`deleteDish` (`db.js:48-54`) clears neither `cookingHistory` rows nor `familyMembers[].preferences[id]`, so a delete
would produce "Unknown" calendar entries, an `unknown` stats bucket, and stale preference keys inflating the counters.

### F2.7 — A new custom dish can't be rated at creation [Medium · certain]
Custom dishes do appear in Family's bulk and per-member views (`FamilyPage.jsx:160`, `:182-201`), but RecipesPage's add
form has no preference controls and closes on save. The natural moment to say "everyone loves this" is lost, and the
dish starts at the default penalty.

### F2.8 — Onboarding: 30 dishes (not 80), one rating for all members, and no global skip [Medium · certain]
`RatingStep.jsx:11` slices to 30, so 50 seed dishes are unratable during onboarding and the README's "80+ dishes"
overstates it. Each tap sets the *same* preference for *all* members (`:19-22`) — no per-member rating. Mid-wizard data
does persist in IndexedDB, but the step index resets on refresh (`useOnboarding.js:7`). Skipping requires three
non-obvious controls, and the progress bar caps at 96.7% (`:49`).

## 3. Data durability and operational risk

### F3.1 — No export, import, backup, or sync; no `navigator.storage.persist()` [Critical · certain]
Grepping `src/` for `JSON.stringify|JSON.parse|createObjectURL|Blob|FileReader|download|backup|navigator.share`
returns nothing. Settings offers only re-seed, reset history, and erase-all (`SettingsPage.jsx:230-248`). The origin
never asks to be exempt from eviction. Clearing browser data, changing phones, or storage eviction destroys everything
with no warning and no recovery. iOS storage eviction specifics are external and device-dependent (WebKit has enforced
a ~7-day cap on script-writable storage for non-home-screen sites), but the repo-level invariant holds regardless: this
app has no defence either way.

### F3.2 — "Re-seed Default Recipes" promises to keep custom recipes and deletes them [Critical · certain]
`SettingsPage.jsx:234` says "Your custom recipes will remain"; `db.js:38` calls `db.dishes.clear()` unconditionally.
`seedDishes` contains no custom recipes by construction, and none of the 80 entries carries an `id`, so they are
re-inserted with **new, higher auto-increment keys** (`clear()` does not reset a key generator). Every existing
`cookingHistory.dishId` and `preferences[oldId]` then points at a deleted row. The cascade (Unknown calendar entries,
collapsed stats, inert preferences) is spec-derived rather than executed, and labelled likely.

### F3.3 — No migration story; erase-all restarts onboarding [Medium · likely]
Only `db.version(1)` exists with no `.upgrade()`. A future schema change without a version bump throws Dexie
`VersionError`, surfaced as an unrecoverable "⚠️ Database Error" screen (`App.jsx:21-24`). `handleResetAll` does
`db.delete()` then reload; recovery depends on `initializeDatabase()` re-seeding, whose default settings carry
`onboardingComplete: false` — so erasing data also throws the user back through the wizard.

### F3.4 — No tests, and CI never lints [High · certain]
`package.json` has no `test` script and no runner in `devDependencies`; no test/spec files exist anywhere.
`deploy.yml` triggers on push to `master`/`main` only (**no `pull_request` trigger**), and runs `npm ci` plus
`npm run build` — never `npm run lint`. None of the defects above would have been caught by the existing gate.

### F3.5 — Accessibility violations [High · certain]
1. **Zoom disabled** — `maximum-scale=1.0, user-scalable=no` (`index.html:6`), WCAG 1.4.4.
2. **No keyboard focus indicator on any `.btn`** — `.btn { outline: none }` (`components.css:42`) with no
   `:focus-visible` replacement, including the main tab bar (`BottomNav.jsx:26`), WCAG 2.4.7.
3. **Urdu text unmarked** — `lang="en" dir="ltr"` (`index.html:2`) with inline `direction: rtl` styles and no
   `lang="ur"`, so screen readers read Urdu with an English voice, WCAG 3.1.1/3.1.2.
4. **Tab bar conveys state by colour only** — no `aria-current`, no `aria-label` on the `<nav>` (`BottomNav.jsx:17-32`),
   WCAG 1.4.1/4.1.2.
5. **Every modal is visual-only** — no `role="dialog"`, `aria-modal`, focus trap, Escape handler, or overlay close
   (`RecipesPage.jsx:147`, `FamilyPage.jsx:175`, `:208`). Zero `role=`/`aria-*`/`tabIndex`/`onKeyDown` in all of `src/`.
6. **Emoji-only preference buttons** — ❤️/👍/🚫 with no `aria-label` or `aria-pressed` (`FamilyPage.jsx:192-194`, `:231-233`).
7. **Unlabelled icon buttons** — month arrows (`CalendarPage.jsx:156,160`), back (`Header.jsx:22-24`), FAB
   (`RecipesPage.jsx:137`), modal closes (`FamilyPage.jsx:179,215`).
8. **10px navigation labels** (`BottomNav.jsx:71`).

The app fails core WCAG 2.2 A/AA checks while being aimed at households whose roles list includes `father`/`mother`.

### F3.6 — "100% Offline-First" overstated; favicon 404s [Medium · certain]
`index.css:1` `@import`s Google Fonts — a render-blocking cross-origin request, and the precache manifest (11 entries)
contains no font CSS, so typography is offline only after one successful online fetch. Every cold start contacts Google,
which sits awkwardly beside the "complete privacy" claim. Separately, `index.html:5` references `/vite.svg`, which does
not exist in `public/` (confirmed 404 live); the real `favicon.svg` is precached but never referenced, and
`vite.config.js:11` `includeAssets: ['vite.svg']` points at the same missing file.

### F3.7 — PWA icon quality [Medium · certain]
Both `pwa-192x192.png` and `pwa-512x512.png` are byte-identical (same MD5), are actually **1024×1024 JPEGs** despite
the `.png` extension and declared sizes, and weigh **452 KB each**. Roughly 904 KB of the 1340 KiB precache is two
duplicate oversized icons — on a product pitched at offline-first mobile use. No `apple-touch-icon` for iOS installs.

## 4. Lint and build health

F1.7), unused `settings` in `getDishScore` (`:79`, so cooldowns filter but never score), unused `label`
(`HomePage.jsx:5`), and `set-state-in-effect` in `SettingsPage.jsx:14` (which also makes React Compiler skip the

`npm run build` — succeeds, 50 modules, 442 kB JS (130 kB gzip), precache 11 entries / 1340 KiB. No chunk-size warning.
`dist/` is git-ignored, so the stale artifact locally is not a shipped risk.

## 6. Future feature prospects, ranked by leverage

1. **Export/import (restore from file)** — not a feature but a prerequisite. Ship before any marketing.
2. **Shopping list generated from the accepted plan** — the highest-value missing feature and the one that turns a
   suggester into a weekly habit. The real job-to-be-done is "decide → list → shop → cook"; only step one is owned.
   Ship a coarse, editable version before investing in ingredient data for all 80 dishes.
3. **Manual logging, edit, and move meals** — restores trust in history, the prerequisite for honest cooldowns and stats.
4. **Ramadan / seasonal mode** — `seasonTags` already includes `ramazan` and `eid` and is read by nothing. Ramadan
   means sehri/iftar meal types rather than lunch/dinner, plus repeat-heavy, hydration-aware planning. The single
   biggest annual meal-planning moment for the target household, and genuinely underserved.
5. **Ingredients and instructions** — `recipe: null` on all 80 dishes. Turns the planner into a cookbook and unlocks
   both the shopping list and a cook-mode.
6. **Device-to-device sharing without a server** (QR / JSON handoff) — keeps local-first intact while fixing
   "only my phone knows".
7. **Guest mode and portion scaling** — headcount varies constantly in these households.
8. **Progressive preference learning** — infer from accepted/swapped/skipped instead of a 30-dish interrogation up
   front. Fixes the onboarding wall and improves the engine with one change.
9. **Pantry and budget awareness** — "what can I make from what's here" is a stronger hook than "what should I make".
10. **Retention surface** — the monthly summary exists with no streak, no discovery, no nudge.

**Strategic caveat:** the no-backend, no-account, fully-offline design is simultaneously a differentiator (privacy,
zero cost, works on cheap Android) and a ceiling (no cross-device, no telemetry, no recurring revenue beyond
donations or content packs). It also can't be retrofitted cheaply: `++id` autoincrement primary keys are the specific
thing that makes later sync a rewrite rather than a migration.

## Round 2 — acceptance measurement, and a verification trap worth recording

Added the metric that actually decides the remaining roadmap: **how often the
household accepts what the planner offers**, split three ways.

| figure | meaning | if it is low |
|---|---|---|
| top-pick acceptance | took the dish offered first | ranking needs work |
| list acceptance | took something from the list | the *pool* is wrong |
| swapped away | rejected the list entirely | the pool is wrong |

That distinction could not be recovered from cooking history: a logged meal might have
been the top pick, an alternative, or a manual entry, and each implies something
different. So an append-only usage-event log now records what was offered and what
happened to it. It is capped at 5000 rows, never leaves the device, and travels in the
backup.

### Two real bugs found while building it

1. **A check-then-insert race.** React double-invokes mount effects, so the same
   suggestion was recorded two or three times. Reproduced deterministically: three
   simultaneous writes produced three rows. Fixed with a synchronous in-flight claim
   taken before any `await`, keeping the database lookup for genuine repeats across
   restarts. Now covered by tests that fire concurrent writes.

2. **Accepted meals were re-logged as offers.** The effect keyed off a derived value
   that changed after a write, so one meal counted as both an outcome and a new
   suggestion.

### Verification trap — read this before browser-testing

**The service worker serves a stale precached bundle, so browser checks silently test
old code.** This cost most of a round: fixes appeared not to work, and phantom
duplicates were blamed on the data layer when the page was running a bundle from
several commits earlier. The give-away was a recorder that was never invoked while
rows still appeared.

Before any browser verification, disable the worker. Unregistering it and then
navigating is *not* enough — the navigation re-activates it. Either launch Chrome with
`--blink-settings=serviceWorkerEnabled=false`, or serve from a context where no worker
is registered. Then confirm the running bundle filename matches what the server
serves:

```js
[...document.scripts].map(s => s.src).join(',').split('/').pop()
```

If those differ, the result describes old code and is worthless.

## Round 3 — the shopping list

The second of the two blocked features, now built. It was blocked on the absence of
ingredient data, and that is resolved by **deriving** a coarse list from what the app
already knows rather than inventing recipes:

- the dish's structured `proteinType`, and
- the words in the dish's own name — `Aloo Palak` really is potato and spinach,
  `Chicken Biryani` really is chicken and rice — plus
- an explicit override table for the few names that imply nothing, such as `Siri Paye`
  (trotters).

A test fails if **any** seeded dish yields no ingredients, so a gap surfaces as a red
test rather than as a quietly short list. Coverage is **80/80**, averaging 1.94 items
per dish. Catching this mattered: the first pass missed `Shaljam` (turnip) and `Arvi`
(taro) entirely, which a test — not inspection — is what would have found.

Output is grouped by aisle (meat, produce, staples, dairy, other), and each line names
the dishes that needed it, so a user can judge the entry rather than trust it. The
window defaults to seven days with a fourteen-day option; past meals are excluded
because a shopping trip covers what is coming.

**Design choice:** the derived portion is recomputed from the plan on every render, so
it cannot drift out of sync with it. Only manual additions and tick state are stored.
Reachable from Home and Calendar rather than as a sixth bottom-nav tab, which would be
cramped on a phone.

**Scope stated in the UI, not glossed:** no quantities, because no dish records them,
and the list is editable to compensate.

## Round 4 — backup consistency, and a destructive-import bug

Went back to the "export/import + local-date safety" part of the objective and found
two defects in it, both real.

**Export was not a snapshot.** It read seven tables with `Promise.all` rather than
inside a transaction, so a write landing mid-export could produce a file whose
cooking-history rows referenced dishes absent from that same file. It now reads inside
one readonly transaction, and a test asserts every history row resolves to a dish in
the payload.

**Validation would have wiped the device.** `importAllData` clears every table before
writing, and an empty `dishes` array was accepted. A truncated or hand-edited backup
would therefore have erased the user's recipes on import — the exact opposite of what
a restore is for. It is now refused, with a message explaining why.

Two smaller integrity fixes fell out of the same thinking: files whose history
references absent dishes are rejected (they restore as "unknown dish" and skew every
statistic that reads them), and preference keys pointing at absent dishes are dropped
(dead keys can never match and they inflate the preference-coverage figure).

The property that matters is ordering — validation runs before the destructive part, so
a rejected import leaves the device untouched. That is now covered by tests and
verified in a browser:

```
before bad import : {"dishes":80,"members":1}
after bad import  : {"dishes":80,"members":1}   data preserved
refusal message   : "Could not restore: This backup contains no recipes,
                     so restoring it would erase yours."
valid file        : "Restored 80 dishes, 1 members and 0 meals."
```
